# PQS hosting and GitHub capability research

Prepared 2026-09-29. Read-only documentation and tool-catalog review. No authenticated hosting inspection, remote commands, settings changes, deployment, or deployment approval was performed for this report. Provider documentation describes available features; it does not establish this account's actual configuration.

## Capability matrix

| Requirement | Documented or observed capability | PQS account status / action |
|---|---|---|
| SSH access | Namecheap documents Manage Shell for shared accounts, disabled by default. Its SSH guide documents port 21098 for shared hosting and different management-dependent VPS ports. [1][2] | Hosting plan, server hostname, actual port, enabled shell and cPanel username unverified. Obtain them from authenticated account details; do not assume 21098. |
| Key authentication | Namecheap supports importing a public SSH key and authorizing it in cPanel; importing an outbound private key is unnecessary for incoming authentication. [3] | No staging/production keys installed or verified. Generate separately through an owner-controlled secure setup and store production private key only in the protected GitHub environment. |
| Forced-command receiver | OpenSSH supports an authorized_keys `command="..."`; `restrict` disables forwarding, PTY and user rc. The original request remains available as SSH_ORIGINAL_COMMAND. A daemon ForceCommand may override the key command. [4] | Namecheap account support and persistence of these options are unverified. Test shell/SFTP/arbitrary-command denial and allowed receiver operations with disposable staging credentials before production use. Never use eval or a shell on the original request. |
| Main document root | cPanel's domain interface does not allow changing the main domain's document root. Changing another root does not move existing files. [5] | Whether pqsensing.com is the account's main domain and its actual root are unverified. Keep the actual root directory intact. Do not replace public_html with a symlink. |
| Release pointer and routing | cPanel documents multiple symlink protection schemes; symlink behavior depends on host policy, kernel protection and web-server configuration. [6] | No positive evidence that the proposed route through a same-owner release-pointer symlink works here. Prove it on staging, including HTTP routes, directory handling and authorization. Fail closed or submit a reviewed alternative. |

This report does not assert it was disabled. |

Verify settings through authorized account surface; do not infer from workflow YAML. |
| GitHub native authoring | Current tool catalog exposes branch/blob/tree/commit/file operations; PR creation, comments, reviews and merge; workflow logs, artifacts and some reruns. | Capability observed in metadata only. Repository access, credentials and permissions must be tested separately. PR approval is not deployment approval. |

## Secure setup sequence

1. Record actual repository workflow state; administratively disable the legacy FTP workflow and deal with any already queued/running deployment before main changes. Preserve its prior file and state as the recovery record. A branch-only PR is not evidence the production trigger is disabled.
2. Through authenticated cPanel or an explicitly authorized secure interface, record domain/root/shell/server/port and public host-key fingerprint. Confirm the fingerprint against an independent authenticated provider channel; a fresh ssh-keyscan result alone is not identity verification. Do not put passwords, private keys, cPanel API tokens or raw backups into chat or the public repository.
3. Make an authorized read-only snapshot and metadata inventory, including hidden files and host-managed paths. Keep snapshot output outside every public root and obtain an encrypted off-host recovery copy. Reconcile its current content against source before treating the source as deployable.
4. Establish staging DNS/TLS and stable authentication/noindex configuration. Determine whether the staging root could also be reached under the main domain; test every alternate route. Auth and noindex are host configuration, so staging and production can consume identical artifact bytes.
5. Install the small reviewed receiver outside the web root with fixed configuration and separate stage/production key restrictions. Keep deploy payloads unable to overwrite the receiver, authorized_keys, routing or configuration. On a shared Unix account these are protocol restrictions, not full operating-system isolation; receiver code correctness remains part of the security boundary.
6. Validate actual same-filesystem rename, symlink routing and ownership. Preserve the existing root, .well-known and all inventoried host paths. Do not enable global FollowSymLinks or disable provider security just to make deployment work.
7. Configure protected environments through the owner's authenticated GitHub settings: Jon required for production, self-review setting compatible with his workflow, administrator bypass disabled, explicit main-only deployment policy, distinct stage/production credentials. Review infrastructure PRs manually; PR rule choices must not require Jon to approve his own authored PR.
8. Run the provided acceptance tests with staging credentials: archive rejection, partial upload, expected-current mismatch, serialized activation, injected health-check failure, rollback, disconnect during activation and subsequent recovery. Demonstrate new release identity after new bytes, and retention of cached old fingerprinted assets. Do not label unexecuted tests passed.
9. Show Jon the actual authenticated preview and exact release tuple, obtain his baseline/cutover decision, and use GitHub's real deployment approval step if no native approval tool exists. Production remains disabled until that gate is satisfied.
